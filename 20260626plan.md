# 2026-06-26 Realtime Voice Upstream Integration Plan

Supersession note, 2026-07-04: this plan is historical implementation context.
The current architecture source of truth is
`docs/design/full-kame-style-realtime-voice.md` plus
`docs/kame-session-v1.md`: reflex -> Gemma direct-audio interpreter -> Hermes
active `/model` oracle. STT/caption/provider transcript work in this plan should
be read as optional witness/fallback evidence unless explicitly promoted by the
interpreter or oracle.

## Objective

Build the KAME-style Discord realtime voice branch into the highest-quality upstreamable implementation by layering in the best proven work from current upstream branches, while preserving the sidecar/oracle architecture that makes our branch differentiated.

For this plan, KAME-style means the human speaks to a lightweight, low-latency
reflex while a separate interpreter turns clipped raw audio plus labeled
transcript hypotheses into promoted evidence for Hermes. The reflex owns the
live voice loop: speech input, turn detection, short acknowledgements, fast
spoken output, and barge-in. A Gemma-style audio interpreter owns corrected
transcript/intent/entity evidence after the cut. Hermes' normal active
`/model` remains the backend oracle for deeper reasoning, tools, memory, and
durable agent work. The frontend model should make the conversation feel
immediate without pretending to be the whole agent, and transcript-looking text
must remain hypothesis evidence unless promoted.

The target is a Discord voice mode that can survive real use:

- `/voice join` works with the existing Discord setup and does not regress legacy voice behavior.
- Receiver/caption evidence is bounded and low-latency enough that witness
  text does not lag several utterances behind or create duplicate Hermes turns.
- TTS playback is continuous and interruptible, not a burst of tiny playback jobs.
- Barge-in stops audible speech quickly and cancels the active model/provider turn.
- The model knows it is in voice mode and does not claim it cannot hear or speak.
- Sidecar failure degrades cleanly with visible status and without breaking text Discord.
- Config is scoped correctly, with secrets in env and behavior in Hermes config.
- The implementation ships with unit, integration, and live evidence strong enough for upstream maintainers to trust.

## Guiding Principles

- Keep the KAME substrate: provider-neutral realtime voice events, sidecar isolation, lightweight frontend model, Hermes backend oracle, session evidence, and replayable diagnostics are the long-term advantage of this branch.
- Preserve the frontend/backend split: upstream direct-realtime work is useful for transport, auth, playback, cancellation, and smoke evidence, but it must not collapse the low-latency interface model into the Hermes oracle.
- Reuse upstream proof where it exists: prefer proven Discord receiver, playback, Realtime API, and barge-in lessons over inventing new versions.
- Keep the default safe: realtime voice remains opt-in and disabled by default. Legacy Discord voice and text paths must continue to pass.
- Split for review: make the final branch presentable as small mergeable PRs, even if development happens on this integration branch.
- Treat live Discord evidence as a release artifact: every major fix should have a focused automated test and at least one captured smoke result before being presented upstream.

## Phase 1: Port The Bounded Receiver And Caption Hygiene

Port the useful parts of PR #42611 into the current plugin path:

- Add a maximum live utterance duration to the Discord `VoiceReceiver` so a long speech segment cannot wait forever for silence.
- Add throttled inbound voice activity timeout refresh so realtime voice packets keep the session alive even when legacy transcript handling is bypassed.
- Add config for whether completed voice transcripts may invoke a fallback text
  agent turn automatically, defaulting to the safer upstream behavior. In full
  KAME mode, completed transcript text is attached as a hypothesis to the
  raw-audio interpreter bundle instead of invoking the agent directly.
- Preserve current `/voice` UX while making the realtime path opt-in.
- Add tests around long utterance flush, timeout refresh throttling, and transcript-agent-turn config.

Acceptance:

- A user can speak continuously and still get bounded receiver/caption events.
- Realtime voice input keeps the Discord voice session from timing out while
  legacy transcript dispatch is skipped or hypothesis-only.
- Existing voice command tests continue to pass.

## Phase 2: Replace The Realtime Mixer Playback Path

Harden playback before adding more providers. The current path should not enqueue every 20 ms PCM frame as a separate mixer child.

Implement a persistent streaming speech path:

- Add a `StreamingSpeechBuffer` or equivalent persistent child/source in `VoiceMixer`.
- Feed realtime TTS PCM into a bounded queue that the Discord audio source drains at Discord frame cadence.
- Return silence while idle instead of closing the source between chunks.
- Support clear/drain on barge-in.
- Apply backpressure and drop policy explicitly, with counters for dropped frames and queue depth.
- Keep the older `play_speech` path for non-realtime TTS.

Use PR #21504's `RealtimeDiscordAudioSource` concept as the model, adapted to the current `plugins/platforms/discord/voice_mixer.py` design.

Acceptance:

- Realtime TTS creates one persistent playback source per active response, not one mixer child per frame.
- Playback can absorb chunk jitter without audible gaps in normal conditions.
- Barge-in clears queued audio immediately.
- Unit tests prove frame sizing, idle silence, clear behavior, queue bounds, and fade/stop interactions.

## Phase 3: Frontend Provider And Sidecar Hardening

Keep the KAME sidecar/oracle contract, but make the lightweight frontend-provider side credible enough to compare with the direct OpenAI branches.

Work items:

- Define the boundary between frontend model and Hermes oracle: the frontend handles low-latency voice interaction, while Hermes handles durable reasoning, tools, memory, and final task execution.

Acceptance:

- Tool calls are impossible unless enabled by current Hermes tool policy.
- Tests cover provider startup, shutdown, cancellation, malformed event handling, and unavailable-provider fallback.

## Phase 4: Barge-In Contract

Make barge-in a strict, testable sequence rather than a best-effort side effect.

Required order:

1. Detect user speech above threshold while assistant audio is active.
2. Immediately stop audible playback and clear queued mixer frames.
3. Send provider cancel if supported.
4. Interrupt the active Hermes/oracle task.
5. Mark the old generation stale so late audio/text cannot resume playback.
6. Start or continue the new user turn.

Implementation details:

- Add generation IDs for active voice responses.
- Gate all TTS chunks and text deltas against the active generation.
- Treat late provider audio after cancel as discarded evidence, not playable audio.
- Add a barge-in latency metric from detection to mixer silence.
- Keep response cancellation provider-neutral and aware of both frontend-provider response state and backend Hermes/oracle turn state.

Acceptance:

- Barge-in stops local playback within the target threshold, initially 200 ms for the automated fake mixer and then measured live.
- Late audio from an interrupted response is dropped.
- The next user turn is not blocked on the canceled response.
- Tests cover double barge-in, cancel failure, late audio, and no-audio idle cases.

## Phase 5: Voice-Aware Agent Behavior

Prevent the June 9 failure mode where Hermes verbally claimed it could not hear or speak.

Work items:

- Keep the realtime voice oracle context explicit: the agent is in a Discord
  voice session, receives promoted voice evidence from the KAME bundle, and can
  reply by voice.
- Make the prompt contract explicit that the low-latency frontend is the voice interface and Hermes is the backend agent/oracle, so the system never describes itself as unable to hear or speak while the frontend is healthy.
- Inject current voice mode, channel, participants, sidecar status, provider status, and fallback reason into the turn context.
- Add a short-response policy for voice mode so spoken replies are concise by default.
- Ensure text fallback messages do not teach the model to deny voice capability when the voice stack is partially degraded.
- Add regression tests for "can you hear me", "use voice", sidecar unavailable,
  TTS unavailable, and transcript-fallback unavailable prompts. STT
  unavailability is only a fallback/caption degradation when the
  raw-audio/reflex/interpreter path is healthy.

Acceptance:

- In healthy voice mode, the model never says it cannot join, hear, or speak in voice.
- In degraded mode, it says the specific failing component is unavailable and keeps the answer short.
- Voice responses are concise unless the user asks for detail.

## Phase 6: Config Scoping And Operator UX

Make configuration reviewable and predictable.

Config plan:

- `discord.realtime_voice.enabled`: default false.
- `discord.realtime_voice.sidecar_url`: config value for deployed sidecar endpoint.
- `discord.realtime_voice.provider`: `reference`, `openai_realtime`, or future provider names.
- `discord.realtime_voice.frontend_model`: low-latency realtime interface model.
- `discord.realtime_voice.preferred_local_oracle_candidate`: optional local
  provider registration hint. Existing status payloads may still expose the
  legacy `preferred_local_oracle_model` name for compatibility, but it must not
  be treated as a voice-specific oracle selector. Hermes backend/oracle model
  selection remains the active `/model` selection.
- `discord.realtime_voice.input_sample_rate`, `output_sample_rate`, and frame sizing where needed.
- `discord.realtime_voice.barge_in.enabled`, threshold, hold time, and cancel timeout.
- `discord.voice_transcript_agent_turns`: fallback/text-oracle compatibility
  only; default false unless maintainers prefer current behavior. Full KAME
  uses transcript hypotheses inside the interpreter bundle instead.
- `realtime_voice.*`: provider-neutral settings shared by Discord and future platforms.
- Env vars only for secrets and deployment-specific overrides such as API keys or auth tokens.

Operator UX:

- `/voice status` should show realtime enabled/disabled, sidecar connected/unavailable, provider, fallback mode, current playback state, and last error.
- `hermes doctor` should validate Discord realtime voice config without requiring a live Discord session.
- Smoke commands should print exact config and provider capability summary.

Acceptance:

- No behavior changes are hidden behind undocumented env vars.
- Config tests verify defaults and overrides.
- Doctor tests cover missing sidecar, missing provider credentials, disabled realtime voice, and healthy reference sidecar.

## Phase 7: Fallback And Shutdown

Sidecar lifecycle needs to be boring and predictable.

Work items:

- Define session states: inactive, connecting, ready, degraded, shutting_down, closed.
- On `/voice leave`, cancel active provider response, clear mixer playback, stop receiver callbacks, close sidecar websocket/process, and await bounded shutdown.
- On Discord disconnect, run the same shutdown path.
- On sidecar crash or timeout, switch to configured fallback and surface status once, not on every packet.
- Make shutdown idempotent.
- Ensure receiver callbacks cannot call into a closed sidecar session.

Acceptance:

- Repeated `/voice leave`, Discord disconnect, sidecar crash, and bot shutdown are idempotent.
- No background task remains after session shutdown in tests.
- Sidecar unavailable at join time results in clear degraded status and functional non-realtime fallback.
